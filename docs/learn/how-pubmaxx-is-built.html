CH 01First principles of a web product

Principle. Every web page is the output of a function that turns a request into bytes. The only real design question is where and when that function runs: on the server before the response is sent, in the browser after it arrives, or once at build time and cached forever. Everything else — frameworks, hooks, hydration — is machinery for choosing that answer per screen.

The request lifecycle, stripped to its bones

When a browser asks for https://pubmaxxing.com/map, a chain runs whether or not you designed it consciously: DNS resolves the host → a TCP+TLS handshake opens a connection → an HTTP GET /map travels to Vercel's edge → a function produces an HTML document → the browser parses it, discovers subresources (JS, CSS, fonts, data), fetches those, builds the DOM, runs the JavaScript, and only then paints. The user's felt experience is dominated by two moments in that chain: Time To First Byte (how long until the server starts answering) and Largest Contentful Paint (how long until the main thing is on screen). Almost every performance decision in this repo is an argument about moving work earlier or later in that chain.

SSR vs CSR vs static — the three places the render function can live

These are not tribes to join; they're tools to mix per route. The App Router's entire reason for existing is to let you pick per component: server components render on the server and ship zero JS; a "use client" boundary marks the sub-tree that also runs in the browser.

Why Next.js App Router here — and the one line that changed the whole rendering model

PUBMAXX is one Next.js 16 App Router app. But there is a subtle, load-bearing decision that overrides the usual "static by default" story. Open proxy.ts (Next 16 renamed the old middleware.ts convention to proxy.ts). It builds a per-request Content-Security-Policy with a fresh nonce so that script-src can drop 'unsafe-inline' — the single most valuable XSS mitigation you can make on a page that runs inline scripts. The comment spells out the trade-off honestly:

// TRADE-OFF (acknowledged): a per-request nonce forces DYNAMIC rendering for
// every route — static generation / ISR / PPR are incompatible with nonce CSP
// because a prebuilt shell can't know the request's nonce.

Read that twice. A security decision (nonce-based CSP) silently made a rendering decision (everything is dynamic, nothing is statically prebuilt). This is the essence of engineering at altitude: choices couple across layers, and the senior move is to see the coupling, price it, and write the price down in the code. The security headers that don't need per-request data — HSTS, X-Content-Type-Options, X-Frame-Options, Permissions-Policy, COOP, Referrer-Policy — stay in next.config.mjs on /:path*; only the CSP moved to the proxy. Knowing which headers must be per-request and which can be static is exactly the kind of distinction that separates "it works" from "it works and I can defend every line."

The render path of /map, traced end to end

Now let's follow one real screen. The URL /map maps to app/map/page.tsx — and it is only 55 lines. It is a server component whose main job is metadata:

export async function generateMetadata({ searchParams }: MapPageProps): Promise<Metadata> {
  const sp = searchParams ? await searchParams : undefined;
  const band = firstSearchParam(sp?.band);
  const crawl = firstSearchParam(sp?.crawl);
  const stopCount = stopCountFromPubsParam(firstSearchParam(sp?.pubs));
  // ... builds OG title/description/image from the crawl encoded in the URL
}

Two things here already teach a lot. First, searchParams is a Promise you await — in Next 16 the request inputs are async, which nudges you to treat the request as data that arrives, not a global you read. Second, the page derives its Open Graph card from the crawl state in the URL: share a link to a specific crawl and the preview image reflects that crawl. The URL is the source of truth for shareable state — a theme you'll meet again in Chapter 3.

The visible page itself renders components/PubMaxingShell, and the actual map is components/PubMapCanvas.tsx, which begins with "use client". That boundary is not incidental — WebGL has no server story. You cannot render a GPU canvas on a serverless function; the map must be constructed in the browser inside a mount effect. So the render path is: server builds the HTML shell + metadata (fast, crawlable, SEO-friendly) → the shell paints instantly → the client boundary hydrates → a single mount effect constructs the MapLibre map, reads CSS custom-property "tokens," and paints every pub as a GeoJSON layer on the GPU. The split is deliberate: the parts that benefit from the server (metadata, first paint, security headers) run on the server; the one part that only works in the browser (WebGL) is quarantined behind exactly one "use client" file.

Hydration: the seam where server HTML meets client JavaScript

There's a moment in the render path that quietly causes more bugs than any other: hydration, when React takes the server-rendered HTML and "adopts" it in the browser, attaching event listeners and reconciling its virtual DOM against the markup that's already there. The rule React enforces is unforgiving: the first client render must produce exactly the HTML the server produced, or you get a hydration mismatch (the infamous React #418) and React may throw away the server markup and re-render from scratch — a visible flash and a correctness hazard. This matters because the most natural thing to do — read localStorage or window.matchMedia during render to pick a theme — breaks hydration, because the server has no localStorage and can't know the user's theme, so server HTML and first client render disagree.

PUBMAXX's theme system (app/layout.tsx + components/ThemeToggle.tsx) is a small masterclass in resolving this. Two cooperating pieces: (1) an inline no-flash script runs synchronously in <head>, before paint, reading localStorage["pubmax-theme"]/prefers-color-scheme and setting html[data-theme] — so the correct theme is applied before React even boots, with no flash; and (2) the toggle reads state via useSyncExternalStore with a deterministic "light" server snapshot, so server HTML and first client render agree (both "light"), and only after hydration does it re-read the real attribute. The <html suppressHydrationWarning> exists precisely because that inline script mutates <html> before hydration. The lesson generalizes to all SSR: anything that differs between server and client must be applied outside React's render — either before it (an inline script) or after it (an effect) — never during it.

The map lifecycle: idempotency in a stateful browser component

One more lesson lives in how components/PubMapCanvas.tsx is built, and it's a distributed-systems idea hiding in a UI file. The map is constructed once in a mount effect, and then its scene is rebuilt on every theme flip (a MutationObserver on html[data-theme] calls setStyle(..., { diff: false }), which re-fires style.load, which re-runs buildScene). That means buildScene must be safely re-runnable - idempotent - because it executes many times over the component's life. So every layer add goes through addLayerOnce (checks getLayer first; a bare map.addLayer on a live style throws "Layer with id X already exists" and aborts the whole scene half-built), and every source is guarded with if (!map.getSource(...)). Motivated animation checks map.isStyleLoaded() before touching any layer, because during a style swap the style is transiently null and getLayer on null throws.

Notice the shape of this: it's the same reasoning as Chapter 7's idempotent writes, applied to a render function instead of a database. "This operation will run more times than you think, possibly concurrently with its own teardown, so it must tolerate re-entry and partial state." A theme toggle is a tiny, local event, but getting its lifecycle wrong crashes the map — so the guards are load-bearing, and the tests pin them. The transferable instinct: whenever an operation can run more than once, design it to be safe to run any number of times, and don't rely on it running exactly once. Exactly-once is as much a fiction in a browser event loop as it is across a network.

Why this matters at scale

At one user, all three strategies feel identical — everything is fast on localhost. The differences only appear under load and latency, which is exactly when they're expensive to fix. A route you casually made dynamic runs a function on every request; at a million requests that's a million function-invocations you pay for and wait on, versus a static asset the CDN serves for free from a city near the user. Conversely, a route you statically cached but which needed per-user data will leak one user's view to another — a correctness and privacy bug that a load test surfaces and a unit test never will. The reason to reason about render location now, at the start, is that it is nearly free to choose and painful to change: retrofitting SSR onto a CSR-only app, or peeling personalisation out of a statically-cached page, is among the more miserable migrations in web engineering. The App Router's per-component model exists precisely so this decision stays local and reversible instead of becoming an architecture you're married to.

There's a second scale axis: the JavaScript you ship is downloaded, parsed, and executed on the user's device — and the slowest device in your user base, not yours. Server components matter here beyond SEO: a server component ships zero JavaScript for its own logic, so the more of your tree renders on the server, the less the user's phone has to chew through before it can respond to a tap. On a mobile-first product like this one, that is not a micro-optimisation; it is the difference between a mid-range Android feeling instant and feeling broken.

Staff-level question to ask yourself For any screen I build: what is the cheapest place this could render, and what is forcing it somewhere more expensive? On /map the answer is "the nonce CSP and the WebGL canvas both force dynamic/client work, and I accept that because the security win and the interactivity are the product." If you can't name the forcing function, you're rendering somewhere expensive by accident.

CH 02The data layer as a contract

Principle. Your data layer is not "the database." It is the contract between your code and durable state — a seam you control. If that seam is a thin interface you own, you can swap what's behind it (Postgres, memory, a mock) without the callers noticing. If it's a framework's client sprinkled through every route, you've married the framework and the wedding is forever. Seams beat frameworks.

The dual-backend store seam

The keyless-dev fact from the intro is enforced by one tiny function. Open lib/storeBackend.ts:

/** Single seam: durable Supabase when env keys exist, process-memory otherwise. */
export function selectStore<T>(memory: T, supabase: T): T {
  return isSupabaseConfigured() ? supabase : memory;
}

That is the whole idea. Every domain store — pint drops, plans, night memories, price confirms, and ~a dozen others being migrated onto this pattern — exposes an interface, then picks an implementation at call time: durable Supabase if the environment has keys, an in-process Map if it doesn't. The callers (route handlers) only ever talk to the interface. The result is the property that makes the whole product demoable on a laptop with no secrets: the same code runs, backed by memory instead of Postgres.

Fail-soft, not fail-silent

The subtle craft is in the same file's runStoreOp and createSchemaMissWarner. When a Supabase-backed store hits a missing table (a migration hasn't been applied, or the schema cache is stale), it invokes that operation's explicit schema-miss policy and warns exactly once per context per process, never silently:

console.warn(
  `[${storeTag}] ${context} durable table missing — applying schema-miss policy (${migrationHint}):`,
  errorMessage(err),
);

And crucially, runStoreOp distinguishes a schema miss from any other error, while each operation decides the honest response. Local and Preview demos may use process memory while a migration is pending. The hardened area-demand, venue-operator, and visit-report write paths refuse that ephemeral fallback in deployed production and surface a 503; their reads may still degrade to an honest empty or cached state. This is the difference between fail-soft (a bounded read degradation) and fail-silent (a write pretends to succeed and loses data). Other dual-backend stores retain their documented policies until they receive the same explicit production audit.

Two Postgres error codes are named constants here because they encode intent, not just failure: 23505 unique-violation is treated as the idempotent-success case for insert-if-absent writes, and 23503 foreign-key-violation means "the referenced row doesn't exist." Reading raw driver error codes and mapping them to domain meaning is a small thing that pays forever.

A convex/ directory exists but is dormant: the locked decision (see fable-implement-prd.md) is "Convex: NOT migrating. Supabase is certified production… convex/ stays dormant. Post-launch decision." The seam is real; the third backend is not wired in.

Why this matters at scale

The value of a seam is not visible on the day you write it; it's visible on the day you have to change what's behind it. Consider the counterfactual: if every one of the ~60 write routes imported the Supabase client directly and called it inline, then "run this locally without secrets," "swap Supabase for a different Postgres host," "mock the store in a unit test," and "add a caching layer in front of writes" would each be a 60-file change with 60 chances to get one wrong. With the seam, each is a one-file change behind an interface the 60 callers never notice. This is the practical meaning of dependency inversion: the callers depend on an abstraction (the store interface) you own, not on a concrete library some vendor owns. Frameworks come and go — the seam is the part of your architecture that survives them.

The fail-soft discipline scales for a different reason: partial failure is the normal state of a large system, not the exception. At one machine, "the database is down" is a binary you notice immediately. Across many serverless instances and a managed Postgres, you will routinely have one table's migration lagging a region, one instance with a stale schema cache, one transient connection blip — and the question is whether each of those degrades one read gracefully or takes down a whole page. runStoreOp's per-context, warn-once, schema-miss-vs-real-error distinction is what turns "a table is briefly missing" from an outage into a logged, bounded, self-healing degradation. Systems that assume total success are brittle at scale; systems that make partial failure a first-class, per-operation decision are the ones that stay up.

RLS as defence-in-depth

The second half of the data contract lives in Postgres itself. PUBMAXX's ADR is blunt: no client-side database access. The browser never holds a Supabase anon key or talks to the database directly; every write goes through a server route that validates and rate-limits first, using a service-role admin client that only exists on the server (lib/supabase.ts). So why bother with Row-Level Security at all, if nothing untrusted ever reaches the DB?

Because defence-in-depth assumes the layer in front of you will someday fail. The migrations turn RLS on and write deny-all-by-default policies: visit_reports has RLS enabled with no write policy and a public SELECT scoped to status = 'visible'; rate_limits has RLS on with no policies at all, making it server-private even if a key leaked. Migration 0023_rls_deny_anon_sensitive_reads.sql exists solely to deny anonymous reads of sensitive tables. If a future bug ever exposed the anon key to the browser, RLS is the wall that still stands. You do not skip the seatbelt because you also have brakes.

The mental model to carry away: every security control has an implicit assumption, and defence-in-depth is the practice of not letting any single assumption be load-bearing alone. "No client DB access" assumes the service-role key never leaks. RLS deny-all assumes an attacker might get a connection anyway. The Postgres CHECK constraints (price within £0–£20, valid status) assume the application-layer validation might be bypassed. Each layer is cheap and each covers the failure of the one above it, so the system stays safe even when — not if — one layer has a hole. When you review a security design, the sharp question is never "is this control correct?" but "what does this control assume, and what catches us when that assumption is false?" A design with an answer at every layer is robust; a design where one clever check is the only thing between an attacker and the data is one leak away from an incident.

The migration ledger as an append-only discipline

There are 50 files in supabase/migrations/. Each is named <timestamp>_<NNNN>_<description>.sql. A migration is an append-only, ordered, immutable record: once a migration has run against production, its checksum is recorded in Postgres's schema_migrations table, and you can never edit or reorder it — you can only add a new one. This discipline is what lets a schema evolve safely across many machines and many contributors. It is also, precisely because it is unforgiving, where the interesting scars live.

War story #1 — the number collisions

Look closely at the ledger and you'll find duplicate NNNN numbers: two 0007s (function_search_path and pub_presence), two 0013/0014/0015 pairs (comment_replies, realtime_publication, index_cleanup, each appearing under two different timestamps), two 0021s. This is the signature of parallel development: several branches (in this repo, several agent lanes — see Chapter 8) each grabbed "the next number" independently, and when they merged, the numbers collided. The lesson is baked into the naming convention: the <timestamp> prefix is the real ordering key that Postgres and the Supabase CLI sort on; the NNNN is a human label that can and does collide. Later migrations quietly stopped using an NNNN at all (20260717055514_plan_completion_arrival.sql) — the timestamp is enough.

War story #2 — the "0039 collision" and why you rename the file, not the history

The brief pointed at "the 0039 collision story," and it is real: two lanes both minted an 0039 migration (a push-tokens table vs a pint-drop daily-dedupe), and the fix was to renumber one to 0040 rather than rewrite anything already applied. The deeper version of the same lesson is recorded in docs/MAIN_RECONCILIATION_2026-07-16.md: the first production push exposed a mismatch where production had recorded migrations 0022–0030 under different timestamps than the Git files carried. The resolution is the important part:

"The files were renamed to the recorded versions; the production history table itself was not rewritten… no remote reset or destructive migration repair is allowed."

That is the whole discipline in one sentence. Production's ledger is the ground truth; Git conforms to it, never the reverse. You align the filenames to what production already ran (commits e005f758, bbf55b52 — "align migration ledger with production") because rewriting an applied migration would desync every environment and there is no undo. When the map and the territory disagree, you fix the map.

A timestamp prefix makes migration collisions loud and recoverable; an auto-incrementing integer makes them silent and corrupting. Pick the ordering key that fails loud.

CH 03Data engineering: determinism, provenance, and war stories

Principle. A data pipeline is a function from raw sources to shipped artifacts. If that function is deterministic — same input, byte-identical output — you can review its diffs, trust its rebuilds, and bisect its bugs. If it's non-deterministic, every rebuild is a small act of faith. Data engineering is the practice of making that function honest: deterministic in its transforms, and provenance-preserving in its content.

The pipeline: export → canonicalize → build:slim

The scripts/ in package.json form a clear chain:

"export:data":        "python3 scripts/export_app_dataset_json.py",
"postexport:data":    "npm run canonicalize:venues",
"canonicalize:venues":"node scripts/canonicalize_venue_dataset.mjs",
"prebuild:slim":      "npm run canonicalize:venues",
"build:slim":         "node scripts/build_slim_index.mjs",
"validate-data":      "node scripts/validate-data.mjs",
"prebuild":           "npm run build:slim && npm run build:pubmaxxing-seed"

Read it as a directed graph. Export (Python) pulls the raw source into a JSON dataset. Its post hook automatically runs canonicalize, which normalises and stabilises the venue records (this is where identity is pinned — see below). build:slim then produces the two artifact classes the runtime actually consumes: public/data/venues_slim.json — the tiny map-pin index shipped to every browser — and server-side detail files (data/generated/venue_detail_index.json + venue_details.jsonl) that back the lazy /api/venue/[id] route. Note the prebuild wiring: the artifacts are regenerated before every production build, so a deploy can never ship a stale index. And validate-data is part of npm run verify, the pre-push gate — bad data fails CI exactly like bad code.

The two-artifact split is a performance decision made in the data layer

Why split into "slim pins" and "server-side detail" at build time? Because the map needs ~1,200 tiny records to draw dots, but a venue's full detail (every price row, heritage, photos) is large and only needed when a user taps one pub. Shipping the whole dataset to draw dots would be wasteful; fetching detail per-tap keeps the initial payload small. This is the same instinct as database normalization, applied to shipped files: put the frequently-read, low-cardinality data in one place and the heavy detail behind a key. The split lives in scripts/build_slim_index.mjs and is why the map's first paint is cheap.

Determinism: byte-identical rebuilds

The reason canonicalization is its own step is determinism. If you re-run the pipeline on the same source, the output must be byte-for-byte identical — otherwise every regeneration produces a noisy diff and you can't tell a real data change from reshuffled JSON key order. Determinism is achieved the boring, correct way: stable sort orders, fixed coordinate precision (lat/lng rounded to a fixed number of decimal places), normalised whitespace and casing, and stable identity keys so records don't move when the source reorders. The payoff is that validate-data can assert invariants and a reviewer can read a data diff and understand it. When you hear "deterministic build," this is the mechanical meaning: remove every source of incidental variation until only intentional change survives.

Content-hashed identity — the keystone

A venue's id is not its position in an array. It is an FNV-1a hash of its grouping key (name | address | lat(5dp) | lng(5dp)), base-36, prefixed venue- (lib/venues.ts, stableVenueIdFromKey). This is content-addressing, and it's why the hand-curated crawls and seeded Pint Drops can hard-code ids like venue-16pnwmm (Prospect of Whitby) that survive the dataset being re-exported and reordered. Tests recompute these hashes from the live dataset, so if a canonicalization change ever shifts an id, CI fails loudly instead of the app silently 404-ing a curated stop. Identity derived from content, pinned by tests — that is how you make a dataset safe to build on.

The data as code: validate-data is a build gate

The move that elevates this from "we have some scripts" to "we do data engineering" is that npm run validate-data is part of npm run verify — the same pre-push gate that runs lint, typecheck, and tests. scripts/validate-data.mjs asserts invariants about the shipped artifacts (schema shape, id stability, size budgets, no orphaned references), and if the data violates them the push is rejected exactly like a type error. This is the practice sometimes called "data contracts" or "data unit tests," and it's the reason a bad refresh can't silently reach production: the dataset is treated as a build input that must pass tests, not as a static file someone occasionally eyeballs. When you hear people say "treat your data like code," this file is the concrete meaning — versioned in git, regenerated deterministically, gated by assertions, reviewed as diffs.

Provenance-first data: the Pint Index evidence rules

PUBMAXX's product promise is "every pint has a story, and history and legend never blur." That promise is a data commitment before it is a UI one. The provenance model in lib/curation.ts defines an origin enum — sourced | contributor | anecdote | demo — and a claim-kind enum for the badge the UI renders. Two rules make it real:

  • Claims never flatten. buildVenueClaims keeps a sourced editorial note and a note-only community drop as separate entries; a heritage note lacking a source is downgraded to needs-source, never merged into an authoritative-looking string. A demo seed becomes a display-only baseline claim, never a contributor/anecdote one that could masquerade as organic signal.
  • Evidence sets provenance, not the client. In validatePintDrop, a priced drop becomes contributor, a note-only drop becomes anecdote — the browser never gets to declare its own trust level. And mergeVenueDrops filters provenance === "demo" out before anything touches a price or the "has a story" flag, so seeded example content can never move a real metric.

The London Pint Index — the headline "cheapest pint" figure — inherits this discipline: a price only counts toward an aggregate if it is a real observed price with acceptable provenance. The About-page statistics were explicitly narrowed (PR #276, CodeRabbit MAJOR fix) to count only venues with accepted price observations. That's the evidence rule in one sentence: an aggregate is only as trustworthy as the weakest row you let into it, so don't let weak rows in.

War story: coordinate-drift dedupe

Real-world venue data has the same pub appearing twice with coordinates that drift by a few metres between sources — a naive exact-match dedupe misses them, and you ship two dots for one pub. The grouping key rounds coordinates to 5 decimal places, which collapses most drift, but that alone can also over-merge two genuinely distinct pubs that share a name and rounded location. The robust fix combines signals: proximity (a distance threshold) and name similarity, so "The Crown" 8 metres away merges but "The Crown" across the borough does not. The lesson is general: deduplication is never a single equality check; it's a similarity function over multiple noisy signals with a deliberately chosen threshold. Get the threshold wrong in one direction you split real duplicates; wrong in the other you merge distinct entities. The tests pin the behaviour so a threshold tweak can't silently regress it.

War story: the label-repair — trusting geometry over scraped labels

Scraped data lies in structured ways. Venue records arrived tagged with a borough label from the source, but those labels were frequently wrong — a pub's stated borough didn't match where its coordinates actually fell. The repair, implemented inside scripts/export_app_dataset_json.py, does the epistemically correct thing: it trusts the geometry over the label. It takes the pub's real lat/lng, does a point-in-polygon test against the actual borough boundaries, and rewrites the borough to whatever the coordinates say — correcting hundreds of rows across many venues. The general principle is one of the most useful in all of data engineering: when two fields disagree, trust the one that's harder to fake. Coordinates come from a map; labels come from whoever typed them. Geometry wins.

Why this matters at scale

Determinism is the property that makes a data pipeline reviewable, and reviewability is what lets a dataset grow past one person's head. When a rebuild is byte-identical, a pull request that changes the data shows a diff that a human can read: these three prices changed, this venue moved boroughs, nothing else. When a rebuild is non-deterministic — keys reorder, floats jitter in the last digit, a timestamp sneaks in — every regeneration produces thousands of phantom changes, the real change hides among them, and review collapses into "looks fine, merge it." At that point your data has no gate, and bad rows enter silently. This is why the canonicalize step is separate and mandatory before build: it is not cosmetic tidiness, it is what keeps the data auditable as it scales from one contributor to many.

Provenance scales for the reason all trust systems do: trust is expensive to earn and instant to lose, and it's lost at the weakest point. A single fabricated "historic" badge on a pub that turns out to be a 2019 chain bar poisons the user's belief in every badge. The never-flatten rule and the demo-filtering rule are not fussiness; they are the mechanism that keeps one bad row from contaminating the aggregate and one seeded example from being mistaken for organic signal. As the community layer grows and more contributors add prices and notes, the provenance model is what lets the product accept messy real-world input without letting that mess move a headline number. The discipline compounds: a dataset that has never lied is one you can build features on; one that has lied once needs a caveat forever.

Staff-level question to ask yourself Can I regenerate this artifact from source and get a byte-identical result — and if not, exactly which step introduced the variance? If you can't answer, you don't have a pipeline, you have a ritual. And for every field you ship: what is its provenance, and would I be comfortable if the badge next to it were shown to the user?

CH 04Performance engineering

Principle. Performance is not a vibe you optimise at the end; it is a budget you enforce continuously and a perception you design deliberately. A budget that isn't a CI gate is a wish. And the number that matters is not when your code finished — it's when the user's eyes saw the thing they came for.

Budgets as gates, measured where the user actually is

PUBMAXX's release performance targets live in e2e/gate-z-performance.spec.ts as a Playwright test that runs at a 390×844 mobile viewport — because the product is mobile-first, and measuring perf on a desktop CI machine would flatter you with numbers no user experiences. The budgets are concrete assertions:

expect(metrics.lcpMs).toBeLessThan(2_500);          // Largest Contentful Paint
expect(metrics.cls).toBeLessThan(0.1);              // Cumulative Layout Shift
expect(metrics.maxInteractionMs).toBeLessThan(200); // INP — interaction latency
expect(metrics.firstPinsMs).toBeLessThan(1_500);    // pins visible on the map
expect(metrics.warmNavigationMs).toBeLessThan(100); // cached tab-to-tab nav
expect(metrics.routeReadinessMs).toBeLessThan(1_500);

These aren't guesses — lcpMs, cls, and maxInteractionMs are the three Core Web Vitals (LCP, CLS, INP), gathered live via PerformanceObserver inside the running page. The two custom metrics (firstPinsMs, routeReadinessMs) encode product-specific "the thing is usable" moments. That is the craft: standard vitals for comparability, custom marks for what your product actually promises.

Reality check The brief referenced an "eager-KB CI gate," "Lighthouse as a CI gate," and a specific "5195KB→2212KB" bundle-reduction story. I could not find those as shipped code: there is no eager-KB token, no Lighthouse step in CI, and no 5195/2212 figures in the repo (they appear only as narrative in a lane's PRD prose). What is real and enforced: (1) the Gate-Z Playwright budgets above; (2) a unit test asserting the shipped slim index stays under its KB budget (__tests__ around venues_slim.json); (3) the two-artifact payload split from Chapter 3. I've taught the mechanisms that actually gate this repo and noted the ones that don't exist so you're not chasing a phantom config.

Two-stage payloads: draw fast, hydrate detail lazily

The concrete payload strategy is the slim/detail split from Chapter 3, consumed at runtime as a two-stage load: the browser first pulls the small venues_slim.json pin index and paints dots almost immediately, then fetches heavy per-venue detail lazily via /api/venue/[id] only when a pub is tapped. Notice how next.config.mjs even teaches Next's file-tracer to bundle the server-side detail files with exactly that dynamic route:

outputFileTracingIncludes: {
  "/api/venue/[id]": ["./data/generated/venue_detail_index.json",
                      "./data/generated/venue_details.jsonl"],
},

This is payload sharding by access pattern: the common path (draw the map) is cheap and eager; the rare path (inspect one pub) pays its own cost on demand. The general move — "don't ship what most users won't look at; fetch it when they do" — is the single highest-leverage front-end performance decision, and it's made here in the data-artifact shape, not in a clever loader.

Perceived vs actual speed

Two mechanisms buy felt speed independent of raw milliseconds. First, speculation rules: the app emits a speculationrules script that prerenders likely next navigations — but deliberately at "moderate" eagerness (hover / pointerdown intent), never "eager"/"immediate" which would over-prerender and waste the user's data. There's a test (e2e/perceived-speed.spec.ts) that asserts the eagerness is exactly "moderate" — a performance restraint encoded as a gate. Second, the App Router's View Transitions flag (next.config.mjs, experimental.viewTransition) wraps route navigations in the browser's crossfade with zero per-element choreography, and degrades to an instant swap where unsupported and to no animation under prefers-reduced-motion. Both are pure progressive enhancement: they make it feel faster without a single new render path.

The first-frame watchdog: trust nothing that hasn't painted

Here is the sharpest performance-and-reliability lesson in the repo, and it's worth internalising deeply. A map can reach a state where the WebGL context is granted, MapLibre's style.load event fires, the scene is built — and yet zero frames are ever painted. The user stares at a permanent blank white rectangle while every signal your code checks says "success." This actually happened (it especially bites inside Instagram/TikTok in-app webviews). The naive checks all lie because they measure readiness, not paint.

The fix (PR #297, in fable-implement-prd.md's ledger, implemented as a map first-frame watchdog) is to subscribe to MapLibre's render event and start a 10-second visible-tab timeout: if no frame has actually rendered by then, tear down the optimism and show an honest no-frame fallback - a Retry button, a list of the cheapest pubs, and a link to /pubs - so the screen is useful even when the GPU never delivered. The sibling pin-reveal and tile-failure guards likewise turn a failed basemap stream into an honest Retry notice instead of leaving a silent flat canvas; lib/mapTileFailure.ts owns that decision.

The principle: trust nothing that hasn't painted. "The promise resolved," "the event fired," "the state says ready" are all proxies for the only thing the user cares about — pixels on glass — and proxies can diverge from reality. A senior engineer instruments the real outcome and builds an escape hatch for when it doesn't happen.

Why this matters at scale

Performance regresses the way a beach erodes: never in one dramatic event, always one grain at a time. Each PR adds "just a little" JavaScript, "one more" blocking fetch, "a small" layout shift — and none of them alone is worth blocking, so without a gate they all merge, and six months later the app is slow and no single commit is to blame. A budget encoded as a failing test converts that slow erosion into a discrete, attributable event: this PR pushed LCP over 2.5s, so this PR fixes it before merging. That is the entire reason the Gate-Z budgets are assertions and not a dashboard someone checks quarterly — a dashboard tells you that you're already slow; a gate stops you from getting slow. At scale, with many contributors (or many agents), the only performance discipline that survives is the one the build enforces.

The perceived-vs-actual distinction scales into real money and real trust. Two apps with identical LCP can feel a second apart depending on whether the first paint is a meaningful skeleton or a blank white void, whether the next navigation was speculatively prerendered, whether a tap gets instant visual feedback. Users don't have stopwatches; they have impatience, and impatience is triggered by uncertainty — "is this broken or just slow?" — more than by absolute latency. The first-frame watchdog is the sharpest form of this: a blank white map isn't slow, it's ambiguous, and ambiguity is what makes a user close the tab. Converting ambiguity into an honest, useful fallback ("here are the cheapest pubs, tap Retry") is worth more than shaving 200ms off a number nobody sees. The scale lesson: measure the vitals for comparability, but engineer the perception, because perception is what churns or retains a million users.

Staff-level question to ask yourself What is the difference between "my code succeeded" and "the user got what they wanted," and am I measuring the second one? If your success signal is an event or a resolved promise rather than an observed outcome, you have a blank-white-map bug waiting to happen.

CH 05Caching layers: the full waterfall

Principle. A cache is a bet that the past predicts the future. The skill is not "add caching" — it's choosing, per asset class, how long you're willing to be wrong, and where. The same app can correctly want cache-forever, revalidate-in-background, and never-cache behaviour on different responses. The mistake is applying one policy everywhere.

The waterfall, top to bottom

A request to PUBMAXX can be answered from four increasingly-distant places: the browser's service-worker cache, the browser's HTTP cache, Vercel's CDN edge, or the origin function. Each layer has its own policy, and they compose. The most instructive file in the whole repo for learning caching is public/sw.js, because it states its philosophy in a comment before it writes a line of logic:

*  1. NEVER break a fresh deploy. Caches are keyed by a per-build VERSION...
*  2. NEVER serve stale HTML for navigations. Navigations are network-first...
*  3. NEVER cache API responses (GET or POST). Last-train times and pint
*     prices must be live or absent — stale data here is a lie (honesty rule).

One strategy per asset class

Asset classStrategyWhy
Static /data/*.json (pin index, dataset, POIs)Cache-first + background revalidateEffectively static between deploys; instant on repeat, quietly refreshed
/data/price_updates/*.jsonNetwork-first (fall back to cache)A price refresh must not be trapped behind a stale SW cache
Map tiles + /_next/static/*Stale-while-revalidate, FIFO-capped at 200 entriesHashed/immutable-ish; unbounded growth over a long session must be trimmed
Navigations (HTML)Network-first → cached page → cached / → /offline.htmlNever serve stale HTML; degrade gracefully when the signal dies (pub cellars!)
/api/* (GET or non-GET)Never intercepted (network-only)Live-or-absent is the honesty rule; a stale train time is a lie

Study why price_updates is the one /data exception: everything else under /data is cache-first because it changes only on deploy, but a price refresh can land between deploys, so it gets network-first. That single carve-out is the whole discipline in miniature — the policy follows the data's actual change frequency, not the directory it happens to live in.

Cache versioning: how a deploy preserves a returning user's offline state

The service worker's caches are namespaced by a per-build version. Activation preserves usable offline entries and retires a superseded cache only when its contents are safely covered. Cache maintenance is best-effort and never shares the promise that delivers a successful network response. Normal write-safe updates still wait for existing tabs; immediate takeover is reserved for replacing the known cache-write-coupled policy. public/sw.js owns the exact migration rules, while docs/evidence/map-blank-basemap/README.md records the storage-pressure reproduction and verification.

CDN & HTTP headers: the year-long edge, the modest browser

The static dataset is ~6 MB and lives at fixed, unhashed URLs, so it can't carry an immutable cache-buster. The header in next.config.mjs threads that needle precisely:

source: "/data/:path*",
"Cache-Control": "public, max-age=3600, s-maxage=31536000, stale-while-revalidate=604800"

Decode it: s-maxage=31536000 lets Vercel's edge hold the file for a year (near-instant TTFB), which is safe because Vercel purges the CDN automatically on every deploy; max-age=3600 keeps the browser copy to one hour so a returning client revalidates and picks up fresh data without a hard block; stale-while-revalidate=604800 lets a stale-but-instant response serve while a fresh one is fetched in the background. Three numbers, three different tolerances for being wrong, one per cache layer. That is what "understanding HTTP caching" actually means.

When no-store is the only correct answer

Every API error in the repo sets Cache-Control: no-store by default — look at lib/apiError.ts, where both publicApiError and apiError set it unless a caller overrides. Dynamic /api/* responses (prices, train times, plan state) are never cached, at any layer, because caching them would be caching a lie. The senior instinct: caching is a tool for data whose staleness is tolerable and bounded; for data where "wrong for even a minute" is a correctness bug, the right cache policy is no cache, and you should be able to say why out loud.

Why this matters at scale

Caching is the highest-leverage and most dangerous tool in the performance kit, and the danger grows with reach. A cache bug on one machine confuses one user; a cache bug at the CDN edge serves a stale or — far worse — someone else's response to thousands of users from a node they'll never think to look at. The classic catastrophe is caching a personalized or authenticated response at a shared layer: one user's "hello, Karan" gets stored under a URL and handed to everyone. This is precisely why the repo's rule "never cache /api/*" and the default no-store on every error response are stated so absolutely — at scale, the cost of accidentally caching one dynamic response is not a stale price, it's a privacy incident with a large blast radius. The per-asset-class discipline is what keeps the enormous win of edge caching (a year-long s-maxage on a 6MB dataset is a colossal TTFB and bandwidth saving) without opening the door to the enormous risk.

Cache invalidation is famously one of the two hard problems in computing, and it gets harder with every layer you add, because a stale value can now be pinned in any of them. The two mechanisms this repo leans on — per-deploy versioning (the SW cache namespace, the CDN's automatic purge) and deliberately short browser TTLs behind long edge TTLs — are both answers to "how do I guarantee a way to bust every layer?" The senior habit is to never introduce a cache without simultaneously designing its escape hatch: a version key, a purge trigger, a revalidation window. A cache you can't invalidate on demand is a bug you've scheduled for a future deploy. At scale, "we can't clear that cache without a full redeploy and a prayer" is the sentence that turns a small content fix into a war room.

Staff-level question to ask yourself For this exact response, how long am I willing to serve a wrong answer — and is that tolerance the same at the browser, the edge, and the service worker? If you can't give three numbers with three reasons, you're caching by habit, not by design.

CH 06API & security fundamentals

Principle. An API is a promise to strangers. The two hard parts are keeping the promise stable as it evolves (so you don't break clients) and keeping it safe from the ones who mean harm (so abuse doesn't sink you). Both are won by treating the boundary as a governed surface, not a pile of route handlers.

The locked, additive error contract

When an API returns errors, clients start depending on the shape of those errors — the field names, the codes. Change the shape and you break them silently. PUBMAXX's public error contract (lib/apiError.ts) is a flat, versioned shape:

export type PublicApiError = {
  error: string;      // human-readable message (back-compatible)
  code: string;       // machine-readable code
  retryable: boolean; // can the client safely retry?
  details?: Record<string, unknown>;
};

Two design choices make this a contract rather than a convention. First, it is additive/locked: the compatibilityFields option lets a route spread in legacy sibling fields, but "canonical error fields always win" — you may add to the envelope, never reshape it. Second, it coexists with a deliberately-separate legacy nested shape (apiError → { error: { code, message, status } }) that older Heritage consumers still depend on, kept apart on purpose so the new contract can be clean without a risky migration. This is API evolution done right: new surfaces get the good contract; old surfaces keep the one their clients already parse; a test enforces the boundary so no one accidentally blends them.

Rate limiting: durable buckets, per-IP and global

Rate limiting is where naive implementations quietly fail on serverless, and this repo learned it the hard way. The durable limiter lives in lib/supabase.ts as checkRateLimitDurable, backed by an atomic Postgres check_rate_limit RPC (migration 0003_rate_limits.sql) — the count-and-decide happens inside one database call so two concurrent requests can't both read "1 left" and both proceed. The IP is only ever a secondary key and is always sha256(salt : ip) before it touches the table or a log, so the limiter never stores a raw address.

The write-surface certification (see below) enumerates the boundary classes: a durable rate limit for public/keyless abuse, plus account, capability, moderator, and confirmation boundaries that compose. Paid-spend routes (the LLM concierge, narrated heritage) and Plan creation pass { failClosed: true } — if the durable limiter is unavailable, they reject rather than let unmetered cost through.

Why in-memory dedup fails on serverless — the broadcast story

Here is the exact bug and fix, because it's a perfect teacher. A feature needed to send a "go-live" push broadcast once per night-signal snapshot. The first implementation deduped with an in-memory Set: "have I already sent this snapshot? check the Set." On a single long-lived server that's fine. On Vercel it is broken by construction — each serverless invocation may be a fresh instance with an empty Set, so N concurrent invocations each think they're first and the broadcast fires N times. The fix (PR #300, implemented by an Opus agent, caught in review — fable-implement-prd.md) replaced the Set with a durable at-most-once claim: a budget-of-1 rate-limit claim keyed on the snapshot's generatedAt, held in the shared Postgres limiter. The first instance to claim it wins; every other instance's claim is denied; the broadcast fires exactly once regardless of how many instances race. Statelessness means shared state must live somewhere shared — Chapter 7 makes this its whole subject.

The forwarded-header spoofing lesson

Client IP on a serverless platform comes from the x-forwarded-for header — which is client-suppliable. If your rate limiter keys purely on it, an attacker rotates the header on every request and each looks like a new client, defeating per-IP limits entirely. This was flagged as a security finding on the Capacitor-foundation PR (#295) and fixed with a global backstop bucket (300/hour) layered under the per-IP limit, plus a regression test that fires 301 requests across 250 rotating IPs and asserts the backstop still trips. The design lesson: on the current deploy target x-forwarded-for is safe because Vercel's edge normalises it, but you never trust that alone — you (a) keep IP a secondary signal, (b) hash it, and (c) put an IP-independent global ceiling behind it so header rotation hits a wall. Trust boundaries are assumptions; write the assumption down and backstop it.

Write-surface certification as a governance pattern

The most transferable idea in this chapter is in docs/WRITE_SURFACE_CERTIFICATION.md plus its enforcing test __tests__/writeSurfaceCertification.test.ts. The rule: every exported POST/PUT/PATCH/DELETE handler in app/api is treated as a reviewed, authority-bearing surface — even a POST that is semantically read-only. The test scans the whole API tree and fails CI if a new mutating route appears without a declared authority/abuse boundary, or if the inventory count changes unexpectedly. Adding "route 61" forces you to classify it (durable-limit? account? capability? moderator? confirmation?) or the build goes red.

This is governance-as-code. Instead of hoping every reviewer remembers to ask "did you rate-limit this write?", the question is asked mechanically, every build, forever. Security controls that depend on human vigilance decay; controls that fail the build endure. Turning a review checklist into a test is one of the highest-leverage moves a staff engineer makes.

The five boundary classes are worth memorizing as a general taxonomy for "who is allowed to do this write," because they compose and most real endpoints need more than one:

BoundaryAnswers the questionExample surface
Durable rate limitIs this keyless caller abusing us / burning provider cost?Events, discovery proxies, Pint Drops, Plan creation
AccountIs this a signed-in owner of the thing?Night Memories, Pub Pal, profiles
CapabilityDoes this caller possess a narrow, server-validated grant?Plan actions, invites, completion
ModeratorIs this a staff operator?Import notes, moderation
ConfirmationHas a one-use token been presented for this consequential act?Night Story publication

And the failure posture is defined per class, which is the part most systems forget: paid-spend and Plan creation fail closed (reject when the durable limiter is unavailable); public community writes fall back to a tightened degraded budget; account/moderator/capability routes reject missing authority before persistence, never after. Deciding, up front, whether each surface fails open or fails closed — and writing it into a certification doc plus a test — is what turns "we have auth" into "we have a defensible authorization model."

Why this matters at scale

An API contract is a liability that compounds with every client that adopts it. At one internal caller, you can change an error shape and fix the caller in the same PR. Once the shape is consumed by a mobile app in the App Store, a partner integration, and a cached SDK you don't control, that same "small" change breaks clients you can't even reach, and the breakage shows up as mysterious errors in someone else's crash logs weeks later. This is why the additive-only rule is non-negotiable at scale: you can always add a field (old clients ignore it) but you can never rename or remove one (old clients depend on it). Keeping the legacy nested Heritage envelope alive alongside the clean flat contract, rather than migrating everything to the new shape, is the mature choice — a slightly less elegant codebase in exchange for zero broken clients. Elegance that breaks a shipped consumer is not elegance, it's an incident.

Abuse control scales super-linearly against you: as the product grows, so does the incentive to attack it, and a limiter that "works" in a load test can fail exactly when it's load-tested by an adversary. The serverless statelessness trap is the archetype — the in-memory dedup Set passed every local test and every code review that didn't think about instance topology, because on one machine it was correct. It was only wrong at the scale where multiple instances run concurrently, which is the only scale that matters in production. The general lesson is that security and abuse-resistance are properties of the deployed topology, not of the code in isolation — you cannot review them by reading a function; you have to reason about how many copies of it run and what they share. And because that reasoning is hard to hold in your head every time, the durable fix (state in Postgres) plus the governance gate (write-surface certification) plus the regression test (301 requests / 250 IPs) form a belt-and-suspenders that keeps the invariant true even after everyone who understood it has moved on.

Staff-level question to ask yourself Which of my security invariants survive a tired reviewer at 2am? Any invariant that lives only in a human's memory is already half-gone. The ones encoded as a failing test — the write-surface census, the CORS test, the eagerness assertion — are the ones you can actually rely on.

CH 07Distributed-systems thinking on serverless

Principle. "Serverless" doesn't remove distributed-systems problems — it hides the servers so you forget you have them. Every function invocation is a fresh, stateless, possibly-concurrent instance. The moment two of them can touch the same logical thing, you are doing distributed systems whether you meant to or not.

Instance statelessness is the whole game

The mental model that prevents most serverless bugs is one sentence: a serverless function has no memory of any other invocation. Anything you put in a module-level variable, a Set, a counter, a cache — is per-instance, ephemeral, and might be a blank slate on the very next request. This is why Chapter 6's in-memory dedup Set failed, and it's why the store seam (Chapter 2) treats process-memory strictly as a dev backend: on Vercel, "memory" isn't shared or durable, so production must reach Postgres for anything that must be seen by more than one request. The corollary the code lives by (teach.md, "The rate limiter fails OPEN by design"): each cold start gets a fresh in-memory budget, so any correctness you need across instances must be pushed into shared durable state.

At-most-once vs at-least-once: choosing your poison

Distributed delivery gives you a choice with no free option:

  • At-least-once: retry until acknowledged. You never lose a message, but you might deliver it twice. Safe if the receiver is idempotent.
  • At-most-once: send it once, never retry. You never duplicate, but you might drop it on failure.

The push-broadcast decision (Chapter 6) is an explicit at-most-once choice: a "go-live" notification fired twice is worse than one occasionally missed, so the durable budget-of-1 claim guarantees the broadcast happens at most once per snapshot. Exactly-once delivery is a myth across a network; what you actually build is at-least-once-plus-idempotency or at-most-once-plus-a-durable-claim. PUBMAXX picks the second for broadcasts and the first for user writes — and being able to say which you chose, and why, per surface, is the mark of someone who understands the terrain.

Idempotency & durable claims: the pattern in Postgres

User-facing writes (creating a Plan, joining it, taking a stop action) take the at-least-once-plus-idempotency route, and the mechanism is worth reading in full. Migration 0035_plan_write_idempotency.sql implements atomic RPCs that combine a Postgres advisory lock with a stored idempotency key:

perform pg_advisory_xact_lock(hashtextextended('plan:create:' || p_idempotency_key_hash, 0));
-- if a row already exists for this key AND the request hash matches → 'replayed'
if existing_plan.creation_request_hash = p_request_hash and existing_plan.id = p_id
  then return 'replayed'; end if;
return 'conflict';   -- same key, DIFFERENT request → refuse
-- ... otherwise insert and
return 'created';

Trace the three outcomes: a client that retries the same create (same idempotency key, same request hash) gets 'replayed' and the operation is a no-op — safe to retry forever. A client that reuses a key for a different request gets 'conflict' — the key is being abused, refuse it. A genuinely new request gets 'created'. The pg_advisory_xact_lock serialises concurrent attempts on the same key so two racing retries can't both insert. This is the canonical idempotent-write recipe — a unique claim + a deterministic replay/conflict decision, made atomically in the database — and it appears across the plan create/join/action RPCs precisely because network retries are inevitable and the UI must be able to resend without fear.

Reality check The push-sender pipeline (PR #300) and its durable at-most-once claim are documented and reviewed in fable-implement-prd.md but the sender code and push-tokens table are not present on this branch — they live on the Capacitor-foundation feature branches. The idempotency pattern I anchored above (the Plan RPCs in migration 0035) is on this branch and is the same durable-claim idea in its most inspectable form. I taught the pattern where you can actually read it.

Why this matters at scale

The cruel thing about concurrency bugs is that their probability scales with success. A race between two instances touching the same row has some small chance of firing per pair of concurrent requests; at ten users a day you may never see it, so it passes every test and every demo and ships with confidence. At ten thousand users a day the same code hits that race constantly, and now it's a duplicated charge, a double-sent notification, a lost write — a production incident that reproduces only under load and therefore only in front of customers. This is why you cannot defer concurrency thinking until "we have scale"; by the time the symptom appears, the bug is already deployed and the fix is a migration under fire. The disciplines in this chapter — push shared state into a durable store, make retryable writes idempotent, choose your delivery semantics explicitly — are cheap to apply before the first line and expensive to retrofit after the first incident.

There's also an organizational scale point hiding here. Idempotency keys don't just protect against network retries; they protect against the client behaving in ways you didn't coordinate — a user double-tapping, a flaky connection auto-retrying, a mobile OS replaying a request after backgrounding the app. As the number of client platforms and network conditions grows, the set of ways a request can arrive twice grows with it, and you cannot enumerate them all. An idempotent write surface is the move that makes the whole class disappear at once: you stop asking "did this specific caller retry?" and start guaranteeing "a retry is always safe, whoever sends it and whyever." That is the difference between defending against known duplicate-causes one at a time and making duplicates structurally impossible — the latter is what survives contact with a real, messy, multi-platform userbase.

Staff-level question to ask yourself If two copies of this function run at the same time and touch the same row, what happens? If your answer is "that won't happen," you've found the bug. The senior answer is always one of: it's idempotent, it's behind a durable claim, or it's provably single-writer — and you can point at the line that makes it so.

CH 08Product & AI engineering: the agent-fleet model

Principle. The way software gets built is itself an engineered system. When your "team" is a fleet of AI agents, the leverage is enormous and so is the failure mode: agents are confident, fast, and wrong in correlated ways. The counterweight is process — specs before code, isolation between workers, adversarial review, and verification that trusts observed truth over any agent's report.

This repo is built with a fleet — and it shows in the artifacts

PUBMAXX is developed by a coordinated set of AI agents, and the operating model is written down. From sol.md and fable-implement-prd.md: an architect role (Fable) plans, writes API contracts, reviews, and gates merges but never merges its own work; a backend/feature role (Sol) reviews and merges in the owner's environment; and model-tiered subagents do the implementation — "haiku=mechanical, sonnet=standard, opus=hard." Each PR in the ledger is tagged with the model that implemented it. That tiering is a cost/quality routing decision: don't spend a frontier model on a rename, don't hand a distributed-systems bug to a small one.

PRD → worktree lanes → adversarial review → e2e truth tables

The pipeline that keeps a fleet from producing correlated slop has four stages, each visible in the repo:

  1. PRD first. The docs/ folder is dozens of PRDs — a feature is specified before an agent touches code. Issue #252 ("The Local") is the spec; lanes build its waves "verbatim." A spec is the shared source of truth that stops parallel agents from diverging.
  2. Worktree lanes. Each agent works in an isolated git worktree on its own branch (the "lanes" — map-lane, header-lane, push-senders, label-repair, and the ~40 others addressable in this very session). Isolation means one agent's half-finished work can't corrupt another's, and the merge is where conflicts surface explicitly — exactly the migration-collision discipline from Chapter 2, applied to all code.
  3. Adversarial review. The architect reviews against the contract and forces fixes. The ledger records it plainly: on PR #295, "Architect review forced 5 fixes (rate limit, error envelope, webDir stub, AASA comment, write-surface certification as route 61)." On PR #300, "Fable review caught the original per-instance Set flaw" — the exact distributed-systems bug from Chapter 7, caught by review before it shipped. Review here is not a rubber stamp; it is an adversary looking for the specific ways this class of change goes wrong.
  4. e2e truth tables. The final arbiter is a large Playwright suite (60+ specs in e2e/) that drives a real browser against a real build. When a lane claims clean but reality disagrees, e2e is what says so.

Verification as culture: what "clean" claimed vs what e2e found

The single most important habit in this repo is distrusting claimed success. The ledger is full of moments where a lane reported green and end-to-end testing found otherwise. The canonical example: a service-worker cache was silently defeating a Playwright test that delayed map tiles — the test passed for the wrong reason (the SW served cached tiles, bypassing the delay), masking a real fallback path that was never actually exercised. The fix (PR #298) was serviceWorkers: "block" on the GL project so the scenario tests the thing it claims to test. Note the shape of that bug: a green test that wasn't testing anything. A culture that merely counts passing tests would never have caught it; a culture that asks "is this test actually exercising the failure it names?" did.

The same instinct produced the first-frame watchdog (Chapter 4) and the "honest zeros" rule you see in the product copy — /tonight literally says "no invented nights; thin nights stay thin" rather than fabricate content to look fuller. An engineering culture that will ship an honest zero is one you can trust with a hard yes.

Prompt orchestration is a systems problem

The AI features themselves are engineered with the same distrust. "The Landlord" (retrieval-grounded pub heritage) is bounded on every axis: temperature: 0, a token cap, a 10s AbortController, and — the load-bearing part — sanitiseModelAnswer rejects the entire answer if it cites a fact id outside the retrieved set. A phantom citation is treated as fabrication, and the system falls back to reading the known facts back verbatim or saying the honest line "…I won't make one up." This is prompt orchestration as a systems problem: the LLM is an untrusted component wrapped in validation, timeouts, and a grounded fallback, exactly as you'd wrap any unreliable dependency. The model is not the system; the bounds around it are the system.

Why this matters at scale

Agent fleets invert the classic bottleneck of software teams. For fifty years the constraint was writing the code; with a fleet, generation is nearly free and the constraint moves entirely to verification and integration — deciding what should exist, and confirming that what was produced actually works and actually fits. This is why the ratio of process to code in this repo looks inverted to anyone used to human teams: dozens of PRDs, a formal write-surface census, an architect that reviews but never merges, a 60-spec e2e suite. That apparatus is not overhead bolted onto the "real" work; at fleet scale it is the real work, because the code was the easy part. The teams that get leverage from AI are the ones that industrialize verification to match the new generation throughput; the teams that just point models at a repo and merge what looks plausible are manufacturing technical debt at machine speed.

Correlated failure is the specific danger that makes this non-optional. Human teams fail in uncorrelated ways — two engineers rarely make the identical wrong assumption — so peer review catches a lot by diversity alone. Agents fail in correlated ways: the same blind spot (the in-memory Set, the green-test-that-tests-nothing, the confident hallucinated citation) recurs across lanes because they share training and priors. Diversity-based review doesn't save you; only adversarial, outcome-observing review does — a reviewer specifically hunting the known failure modes, and an e2e layer that observes real behavior rather than trusting reports. The scale lesson generalizes beyond AI: any time your generation capacity outruns your verification capacity, quality is bounded by verification, and the smart investment is there. The Landlord's bounds (temp 0, timeout, phantom-citation rejection, grounded fallback) are this same philosophy applied to the model inside the product — wrap the fast, confident, sometimes-wrong component in verification, whether that component is an LLM feature or an LLM building your features.

Staff-level question to ask yourself When a worker (human, agent, or model) tells me it succeeded, what independent signal confirms it — and is that signal actually observing the outcome, or just re-reading the claim? The whole apparatus of PRDs, isolated lanes, adversarial review, and driven e2e exists to answer that question mechanically instead of trusting a confident report.

CH 09Mobile / native strategy

Principle. "Should we build a native app?" is really three questions: what capabilities do we need that the web denies us, how much duplicated surface can we afford to maintain, and how do we keep the native shell from infecting the web bundle? The best answer is usually the least native thing that unlocks the capability you actually need.

The tradeoff space

ApproachYou getYou pay
PWA (installable web)One codebase, instant updates, offline via SW, add-to-home-screenNo App Store presence; limited push on iOS historically; no deep native APIs
Wrapper (Capacitor/Cordova)App Store presence + native push + camera, over your existing web appA native shell to maintain; store review cycles; some seams to bridge
Full native (Swift/Kotlin)Best performance & platform fidelityA second (or third) full codebase; features ship 2–3× slower

The decision: PWA-first, then a remote-URL Capacitor wrap

PUBMAXX's locked distribution decision (fable-implement-prd.md, "grilled with the owner"): Capacitor wrap of the existing PWA + native push + real in-app camera. No static export — a remote-URL shell over pubmaxxing.com. Full native rebuild rejected. Unpack the phrase "remote-URL shell": instead of bundling the web assets into the app binary (a static export), the Capacitor app is a thin native shell whose webview simply loads the live pubmaxxing.com. The consequence is the whole reason to do it this way: web fixes ship instantly to native users without an App Store review, because the native app is a window onto the same server everyone else hits. You get store presence and native push/camera for the ~1% of capabilities the web can't do, while keeping the 99% single-codebase, instant-update velocity of the web. That is the least-native thing that unlocks the needed capability — precisely the senior instinct.

The order matters too and was argued explicitly: mobile web excellence first, wrap second. The owner directive — "users must love the site and beg for the app first" — treats the App Store as something you earn with a great mobile-web experience, not a checkbox you rush. Sequencing is strategy.

The isNativeApp seam keeps the web bundle clean

The risk with any wrapper is that native-only code leaks into the shared bundle — every web user downloads camera-bridge and push-registration code they'll never run. The defence is the same seam pattern as the data layer (Chapter 2): a single isNativeApp / native-platform detector behind which the native paths (nativeCamera, nativePush) hide, so the web build tree-shakes them away and the web bundle stays lean. One boundary, honestly labelled, quarantines an entire platform's concerns — just like the one "use client" line quarantines WebGL and the one selectStore quarantines the backend choice. The recurring lesson of this whole codebase is that a good seam is worth more than a good framework.

Reality check On this branch, the Capacitor shell, the ios/ scaffold, and the native seams (lib/nativePlatform, nativeCamera, nativePush) are not present — they live on the feature branches behind PR #295 and are documented in fable-implement-prd.md. What is shipped here is the PWA foundation the wrap will sit on: the service worker (public/sw.js), public/manifest.webmanifest, add-to-home-screen, and the mobile-first shell (Map · Tonight · Moment · Stories · You). I've taught the decision and its rationale as the documented, owner-grilled plan it is — accurate, but not yet merged to this line.

Why this matters at scale

The dominant cost of a native strategy is not building it — it's maintaining every copy of every feature, forever, in parallel. A full native rebuild means that from that day on, every feature ships two or three times (web, iOS, Android), every bug is fixed two or three times, and the platforms drift because a fix lands on one before the others. That parallel tax is invisible in the first month and dominant by the second year; it is the single most common reason small teams slow to a crawl. The remote-URL wrap is a direct attack on that tax: because the native app loads the live site, features and fixes ship once and reach native users the moment they deploy — no rebuild, no App Store review latency in the critical path. You accept a thin native shell to maintain in exchange for keeping your feature velocity at web speed across all platforms. For a product that lives or dies on iterating fast, that trade is almost always correct until a specific capability or performance need forces otherwise.

The seam matters at scale for a subtler reason: a leaky platform boundary taxes the majority to serve the minority. If native-only code (camera bridges, push registration, App Store receipt handling) isn't cleanly behind isNativeApp, it gets bundled into the web build that 99% of users load, so every web visitor downloads and parses code that can never run for them — a permanent, invisible weight on your most-trafficked surface to support your least-trafficked one. Clean seams keep the cost of a capability localized to the users who actually use it. This is the exact same principle as the two-artifact data split (don't ship venue detail to draw dots) and the "use client" boundary (don't ship WebGL to the server) — the codebase applies "make each user pay only for what they use" at the data layer, the render layer, and the platform layer alike. That repetition is not a coincidence; it's a house style, and recognizing a house style is how you learn to make decisions that fit a codebase instead of fighting it.

Staff-level question to ask yourself What is the smallest amount of "native" that unlocks the one capability I actually can't get on the web — and what seam keeps that native code from taxing every web user? If you're reaching for a full native rebuild, be sure the capability gap justifies a second codebase; usually a wrapper behind an isNativeApp seam is the honest answer.

CH 10What staff+ looks like

Principle. The gap between senior and staff is not more code or harder algorithms. It is judgement: knowing what not to build, telling the truth when the truth is a zero, correcting the premise of the task instead of executing a flawed one, and treating merge order and risk as first-class design. Staff engineers are paid for the decisions they refuse to make hastily.

Refusing scope: the things this repo deliberately does not build

Open docs/PRD_ENDGAME_TRUST_SOCIAL_ROADMAP_2026-07-07.md and find the Out of Scope list: "Payments, bill splitting, or pub-owner dashboards. Taxi booking. Storing home addresses by default. Scraping competitor price/review sites. Encouraging alcohol volume, streaks, or speed drinking. Multi-city expansion before London is excellent." Every line is a plausible, tempting feature someone asked for, and every line is a deliberate no. Bill-splitting in particular is the classic scope trap — it sounds small, it's a payments-and-liability swamp, and it's off the core promise. Writing your non-goals down, with as much conviction as your goals, is a staff-level act: it protects focus, and it makes every future "can we just add…" a two-second decision instead of a meeting.

Honest zeros

The product will show you a zero rather than fake a number. /tonight ships the copy "no invented nights; thin nights stay thin." The Landlord says "I won't make one up" rather than hallucinate history. Demo seeds are tagged and filtered out before they can move a real metric. The store returns a 503 rather than pretend a write persisted. Every one of these is a choice to let the product look less impressive in exchange for being trustworthy. That trade — credibility over vanity — compounds; a product (and an engineer) known for honest zeros earns the benefit of the doubt on everything else.

Premise correction

This very document is an example. The brief asked me to teach an "eager-KB" gate, a "5195KB→2212KB" story, a Convex backend in the store seam, and a standalone "0039" migration — several of which don't match the shipped code. The staff move was not to invent plausible-sounding code to satisfy the prompt, nor to silently drop the mismatches, but to correct the document to reality and flag exactly what I changed and why (every red box in this guide). When the task's premise is wrong, executing it faithfully produces confident nonsense. Correcting the premise — respectfully, with evidence — is the higher form of doing the job. You saw the same instinct in the migration reconciliation ("production is ground truth; Git conforms to it") and in the fleet's review culture. Reality is the authority; the spec is a hypothesis about reality.

Merge order as risk management

Read the "Suggested merge order" in fable-implement-prd.md: "#295 → #299 → #300 (stack)… #276, #296, #297, #298 independent, any order." That is not bureaucracy — it is sequencing risk. The stacked PRs must land in dependency order or they break; the independent ones are explicitly marked so they can parallelise safely. The whole docs/MAIN_RECONCILIATION_2026-07-16.md exercise — twelve commits reconciled one by one, each marked "integrated" against the mobile line, with a release rule that "a Vercel READY state is not sufficient: both apex and www must be smoke-tested after aliasing" — is risk management dressed as a merge. Staff engineers think about the order operations happen in and what must be verified between them, because most production incidents are not bad code, they're good code applied in the wrong order or promoted without the last check.

Judgement in the small: the constant-time admin gate

Staff-level judgement isn't only visible in big roadmap decisions; it shows in twenty-line functions. The moderator token check (lib/adminAuth.ts / the safeTokenEqual helper referenced in teach.md) doesn't do if (provided === expected). It sha256's both sides and compares with timingSafeEqual, because a naive string comparison returns faster when the first character is wrong than when the first ten match — a timing side-channel that lets an attacker recover a secret byte by byte by measuring response times. Almost no one exploits this on a small app; the reason to write it correctly anyway is that "almost no one" is not "no one," the correct version costs three extra lines, and a codebase that gets the twenty-line security details right is one you can trust on the two-thousand-line ones. Judgement is largely the accumulated habit of not cutting the corner that's cheap to cut and expensive to have cut.

A real reading list, per discipline

These are real books and papers, chosen to deepen the exact muscles this repo exercises. No filler.

Distributed systems & data (Chapters 2, 6, 7)

  • Martin Kleppmann — Designing Data-Intensive Applications (2017). The single best book on the seam between your code and durable state: replication, idempotency, consistency, delivery semantics. Every idea in Chapter 7 is treated rigorously here.
  • DeCandia et al. — "Dynamo: Amazon's Highly Available Key-value Store" (SOSP 2007). The paper that made "eventual consistency" and quorum tradeoffs mainstream; read it for how a real system picks its poison.
  • Nygard — Release It! (2nd ed., 2018). Stability patterns — circuit breakers, bulkheads, fail-fast, timeouts. The intellectual ancestor of this repo's fail-soft/fail-closed limiter decisions.
  • Pat Helland — "Life beyond Distributed Transactions: an Apostate's Opinion" (2007/2016). Why idempotency and durable claims replace the transaction you wish you had — exactly the migration-0035 pattern.

Web platform & performance (Chapters 1, 4, 5)

  • Ilya Grigorik — High Performance Browser Networking (O'Reilly, free online). The request lifecycle from DNS to paint, in depth. Chapter 1's waterfall, rigorously.
  • web.dev — Core Web Vitals & the "Learn Performance" course (Google, ongoing). The canonical, current source for LCP/CLS/INP — the exact metrics gated in gate-z-performance.spec.ts.
  • Jake Archibald — "The offline cookbook" and the Cache-Control chapters of MDN. The definitive treatment of service-worker strategies (cache-first / SWR / network-first) that public/sw.js implements line for line.

Security (Chapter 6)

  • OWASP — Application Security Verification Standard (ASVS) and the Cheat Sheet Series. Turn "be secure" into a checklist you can encode as tests — the spirit of the write-surface certification.
  • Michal Zalewski — The Tangled Web (2011). Still the clearest explanation of browser security models, CSP, and why 'unsafe-inline' is the enemy the nonce in proxy.ts is fighting.

Data / AI engineering (Chapters 3, 8)

  • Kleppmann (again), plus Reis & Housley — Fundamentals of Data Engineering (2022). The pipeline lifecycle, determinism, and data-quality thinking behind Chapter 3.
  • Sculley et al. — "Hidden Technical Debt in Machine Learning Systems" (NeurIPS 2015). Why the code around the model is the system — the framing behind Chapter 8's "bounds around the LLM are the system."
  • Lewis et al. — "Retrieval-Augmented Generation…" (2020). The grounding pattern The Landlord uses: retrieve first, then generate strictly over what you retrieved, and reject anything ungrounded.

Judgement & craft (Chapter 10)

  • Will Larson — Staff Engineer (2021) and An Elegant Puzzle. The definitive modern texts on what the staff+ role actually is: scope, influence, and technical judgement over raw output.
  • Fred Brooks — The Mythical Man-Month (1975/1995). Still correct about parallelism, communication cost, and why adding workers to a late project makes it later — read it against this repo's agent-fleet coordination.
  • Kahneman — Thinking, Fast and Slow (2011). Because premise-correction and honest-zeros are, at bottom, about noticing when a confident fast answer (yours, a model's, a spec's) needs the slow one.
The one habit under all of it Across every chapter, the same move recurs: find the seam, make the invariant a gate, prefer the honest answer, and correct the map to the territory. Seams over frameworks. Tests over vigilance. Zeros over vanity. Reality over the spec. Do those four things consistently and the "staff-level questions" at the end of each chapter start answering themselves — which is, in the end, what staff-level actually feels like from the inside.

How to keep learning from this repo

A curriculum is only useful if it changes what you do next. Here is how to turn this codebase into an ongoing teacher rather than a one-time read:

  • Read the comments as design docs. The most valuable prose in this repo is not in docs/ — it's the block comments in next.config.mjs, proxy.ts, public/sw.js, and lib/storeBackend.ts. Each explains a trade-off, not just a mechanism. When you write code, aspire to comments that a stranger could learn the reasoning from, because future-you is that stranger.
  • Follow one request all the way down. Pick a single action — submitting a Pint Drop — and trace it: the composer component → usePintDrops → POST /api/pint-drops → validatePintDrop → the rate-limit gate → selectStore → the Supabase insert + photo upload → the RLS policy on visit_reports. Following one thread through every layer teaches more than reading ten files in isolation, because it shows you the seams and how they compose.
  • Read the tests to learn the invariants. The __tests__/ and e2e/ directories are an executable specification of what must stay true: demo seeds don't move prices, decodeCrawl never throws, the write-surface census is exact, prerender eagerness is "moderate." When you want to know "what is this system actually promising," read what it refuses to let break.
  • When something looks over-engineered, find the scar. Nearly every guard, fallback, and belt-and-suspenders in this repo exists because something once went wrong — the blank map, the double broadcast, the migration collision, the spoofed header. Before you simplify a defensive-looking piece of code, find the war story that put it there. Chesterton's Fence is the whole game: don't remove the fence until you know why it was built.
  • Practise premise-correction on yourself. The next time a task, a ticket, or a model hands you a plan, ask "is the premise even right?" before executing. This document exists because that question was asked of its own brief. Making it a reflex — respectful, evidence-backed, and applied to your own confident first drafts too — is possibly the single highest-return habit in this entire guide.

The through-line of all ten chapters is one disposition: be honest with the machine and with the user about what is actually true. Render where it's actually cheapest. Cache only what's actually safe to be stale. Show the zero when the answer is actually zero. Refuse the write when the store actually can't keep it. Correct the map when it actually disagrees with the territory. Everything technical in here — seams, budgets, idempotency, provenance, certification — is machinery in service of that one honesty. Build that way and the systems you make will be trustworthy, which is the only reputation, for a product or an engineer, that compounds.
