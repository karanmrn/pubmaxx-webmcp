# PUBMAXXING — Next-Wave Ideas (2026-07-07)

**Brief:** ideate the next wave of features that make the product *more interactive, more
user-friendly, and faster-feeling*, grounded in research on sticky consumer social apps,
map-product interaction patterns, and perceived-performance techniques for map-heavy PWAs.

**How to read this doc:** each idea has a one-line pitch, the user story it serves (tied to the
PRD's generational surfaces), effort (S/M/L), difficulty (low/medium/high per the PRD's Fable
routing rules — Fable takes low/medium, high is the senior lane), dependencies, and an honest
*"why this might fail"* line. Ranked into three tiers: **(A) do-next** (high value, low risk),
**(B) strong bets needing design**, **(C) speculative**.

> **unavailable this session** — every `firecrawl_search` call returned HTTP 401 (auth). I fell
> back to the built-in `WebSearch`/`WebFetch` tools and the codebase + PRD. Sources are cited

## What the research says (mechanics, not vibes)

**Sticky consumer-social loops (Untappd / Letterboxd / Strava / BeReal / Partiful):**
- **Badges as the distinctive hook.** Untappd's most-cited feature is its badge system — local
  badges, venue badges, special/event badges — that reward *specific* logging behaviour, not just
  volume. A longitudinal study frames these as the core retention driver (and flags the ethics of
  gamifying drinking — worth respecting). [1][4][6]
- **Low-friction social validation.** Strava's "kudos" is a one-tap lightweight ack; Partiful's
  guest-list transparency ("see who else is coming the moment you RSVP") creates a *social
  snowball* that converts undecided people. [1][7]
- **Personal archive as investment.** Letterboxd's diary/watchlist turns activity into a
  collectible personal history that users don't want to abandon — the switching cost *is* the
  product. [1]
- **A single daily ritual + spontaneity.** BeReal's once-a-day prompt manufactures a shared
  moment with no filters. Niche apps win by owning one honest ritual, not by being everything. [1]
- **Zero-account, link-first onboarding.** Partiful skips account creation — phone number + link,
  RSVP instantly. Friction removal is the growth mechanic. [7]

**Map-product interaction patterns (Snap Map / Google Maps / Apple Maps):**
- **Heatmap of activity.** Snap Map shows warmer colours where more people are posting — you read
  "where it's kicking off" *before* zooming in. Geo-Stories let co-located people contribute to one
  shared, location-tagged story. Location only updates when the app is open (privacy-forward). [8][9]
- **Live busyness / popular times.** Google Maps aggregates anonymized, differentially-private
  location history into per-hour busyness and *area* busyness (combining nearby venues) — the "is it
  worth going" signal. [10][11]
- **Curated guides + collaborative lists.** Apple's Curated Guides and Google's saved-place Lists
  turn a map into shareable, followable collections — a map as a set of authored chapters. [10]

**Perceived performance for map-heavy PWAs:**
- **Skeletons over spinners.** In 2026 generic spinners are an anti-pattern; layout-matching
  skeletons reduce perceived wait and give structural stability. [12][13]
- **Optimistic UI decouples feedback from the network** — the update "tricks the brain" into
  perceiving the UI as faster than the API. [2][14]
- **View Transitions API** captures before/after snapshots and animates natively while preserving
  focus/accessibility — closes the web-vs-native gap for map↔feed navigation. [3][5]
- **Speculation Rules** prerender/prefetch the *likely next* page so navigation is essentially
  instant. [12][15]

**Cross-check against the repo (so we don't re-propose shipped work):** already BUILT — Spill
composer (`components/map/spillComposer.css`, #24), Chaos Score (`lib/chaosScore.ts`), Rounds
(`app/rounds`), presence + "Tonight" lane, Ledger/Legacy mode, service worker
(`public/sw.js`), and `app/map/loading.tsx`. **Not yet present:** View Transitions API,
Speculation-Rules prefetch, hover/intent prefetch of venue sheets, an Untappd-style badge *event*
system, a live area-busyness heatmap layer, collaborative/followable lists, and a daily ritual
prompt. Those gaps shape the ideas below.

## Tier A — Do next (high value, low risk)

### A1. Prefetch-on-intent for the venue sheet
**Pitch:** the instant a thumb hovers/press-starts a pin, speculatively fetch `/api/venue/[id]` and
warm the sheet so it opens with data already in hand.
**User story:** map-as-living-instrument (#14) + the "map must feel faster than the landing" thesis
— target map-tap → first interactive pin < 1.5s p95.
**Effort:** S · **Difficulty:** low (client fetch + cache on an existing seam; no schema).
**Deps:** none (the slim-index + `/api/venue/[id]` cache already exist).
**Why it might fail:** on mobile there's no hover; press-start prefetch can waste bandwidth on
scroll-bys — needs a short intent delay + dedupe so it doesn't hammer the API.

### A2. Optimistic Spill posting with an instant preview card
**Pitch:** the moment a user hits "Spill", render the final OG-style card immediately (local blob +
entered price) and reconcile with the server in the background; failures roll back gently.
**User story:** The Spill / The Lock-In (Gen Z speed) — "Spill from the map in < 3 taps"; ties to
Spill-completion > 70%.
**Effort:** M · **Difficulty:** medium (`useOptimistic` seam already used in `usePintDrops.ts`;
add rollback + a pending state to the card).
**Deps:** none for memory backend; photo upload path already exists.
**Why it might fail:** photo upload is the slow part — an optimistic *text* card that then shows a
"photo uploading…" shimmer is honest; faking a finished photo card that later fails would erode the
provenance-trust moat.

### A3. Skeleton + progressive pin hydration for `/map`
**Pitch:** replace the abrupt map mount with a pitched-London skeleton (outline + pulsing
price-coloured dots), paint cached/optimistic pins first, then hydrate live.
**User story:** the PRD's *#1 remaining gap* — the map's first impression (#35).
**Effort:** M · **Difficulty:** medium (extend `app/map/loading.tsx` + a cached-pins-first paint;
reads slim index).
**Deps:** slim index (shipped). Respect `prefers-reduced-motion` for the pulse.
**Why it might fail:** a skeleton that doesn't match the real layout increases perceived jank; the
pulsing-dots motif must be tuned against the colourful base so it reads as "loading", not "live".

### A4. One-tap Kudos ("Cheers") reaction with haptic + count-up
**Pitch:** a single dominant lightweight ack on every Spill — a "Cheers 🍻" — distinct from the
5-reaction palette, with an optimistic count-up and (mobile) haptic tap.
**User story:** social gravity (#34) + The Lock-In virality — Strava-kudos-style frictionless
validation. [1]
**Effort:** S · **Difficulty:** low (reactions store already dual-backend; add one canonical type
+ optimistic increment).
**Deps:** none (memory + Supabase reaction seam exists).
**Why it might fail:** yet another reaction could dilute the existing 5; needs to be *the* primary
tap, visually, or it's noise.

### A5. "Made the last train" auto-badge on a Spill
**Pitch:** when a Spill is posted from a venue where Last Pint says the user can still get home,
stamp the card "🚊 made the last train" — turning the signature utility into shareable social proof.
**User story:** feed context (#36: "made the last train") + Last Pint signature utility — no new
surface, just wiring two shipped systems together.
**Effort:** S · **Difficulty:** low (Last-Pint decision shape + Spill composer both exist).
**Deps:** none.
**Why it might fail:** TfL can be down at post time (`live_data_unavailable`) — the badge must only
appear on a genuine live decision, never a guess, or it becomes an untrustworthy claim.

## Tier B — Strong bets needing design

### B1. Live area-busyness heat layer ("where it's kicking off")
**Pitch:** a Snap-Map-style warm-colour overlay driven by tonight's *presence + Spill density*
(not tracked location), so you can see which corner of London is alive before you commit.
**User story:** The Lock-In "pulsing map dots / Tonight" + explore-London — the honest,
privacy-safe version of Google's area busyness. [8][10][11]
**Effort:** L · **Difficulty:** high (map aggregation layer + real-time density; senior lane).
**Deps:** presence/Spill data (shipped); ideally Realtime (#37). **Privacy:** aggregate-only,
session-scoped, never per-user location — matches the out-of-scope "no home-address / no movement
profile" rule.
**Why it might fail:** sparse early data makes the map look dead (a cold-start heatmap is worse
than none) — needs a graceful "quiet tonight" state and possibly a decayed 7-day baseline.

### B2. Badge *events* / seasonal quests (honest, opt-in)
**Pitch:** Untappd-style time-boxed badge events layered on the *existing* computed passport stats —
e.g. "Thames-side Thursday", "visit 3 boroughs this month" — surfaced only in Lock-In mode.
**User story:** Pint Passport as collectible identity (#29) + Letterboxd-diary investment. [1][4][6]
**Effort:** M · **Difficulty:** medium (badges already computed in `computeBadges`; add a
time-boxed quest definition + progress UI).
**Deps:** none for memory; richer with auth (#31) so progress persists per account.
**Why it might fail:** gamifying drinking is ethically loaded (the Untappd study flags this) —
quests must never push volume ("drink more"); frame around *places/stories explored*, and a Boomer
in Ledger mode must never see them.

### B3. Collaborative / followable Lists ("my locals", "date-night")
**Pitch:** the PRD's custom-lists (#33) upgraded into Apple-Guide/Google-List-style *followable,
shareable* collections with an OG cover — a map as authored chapters.
**User story:** custom lists (#33) + crawl-story authorship (#35) — "curate pubs like film lists".
**Effort:** M · **Difficulty:** medium (list model + one render seam; the store pattern exists).
**Deps:** **needs Supabase auth enabled** for durable ownership/following (Epic D). Works
read-only/demo before that.
**Why it might fail:** without auth, "my list" is device-local and lost on clear — value is thin
until ownership ships; risks overlapping with Crawl Stories if the distinction isn't crisp
(list = places, crawl = ordered route).

### B4. View Transitions between map ↔ feed ↔ venue
**Pitch:** use the View Transitions API so the shared pin/photo *morphs* into the sheet and the
feed card, making navigation feel native and continuous instead of a hard swap.
**User story:** faster/more-alive thesis + mobile sheet polish (#14) — closes the web-vs-native gap. [3][5]
**Effort:** M · **Difficulty:** medium (Next App Router + `startViewTransition`; progressive
enhancement, no-op where unsupported).
**Deps:** none; must respect `prefers-reduced-motion` (fall back to instant).
**Why it might fail:** browser support + MapLibre canvas snapshots can be janky (a WebGL canvas
doesn't transition cleanly); scope to DOM chrome (cards/sheet), not the map canvas itself.

### B5. Speculation-Rules prerender of borough & venue pages
**Pitch:** declaratively prerender the *likely next* borough/venue page while the user browses, so
tapping through the explore-London loop is instant.
**User story:** explore-London chapters (#28) + perceived speed. [12][15]
**Effort:** S · **Difficulty:** medium (a `speculationrules` script + eager/moderate ruleset;
needs measurement to avoid over-prerendering).
**Deps:** none.
**Why it might fail:** prerendering server-rendered pages costs bandwidth/compute and can trigger
analytics/side-effects early; must scope to safe GET routes and cap concurrency.

### B6. Group presence in The Round — "your crew is here"
**Pitch:** in an active Round, show crew members' *self-shared* presence on the map (Snap-Map
friend-dots, but scoped to the Round code, app-open-only), so a live crawl assembles itself visibly.
**User story:** The Round (all, group) — "a crawl that builds itself live as friends add Spills". [8]
**Effort:** L · **Difficulty:** high (real-time presence scoped to a group; senior lane).
**Deps:** Rounds (shipped) + Realtime (#37). **Privacy:** opt-in, Round-scoped, app-open-only,
never background — respects the no-DMs / no-tracking scope.
**Why it might fail:** location sharing among friends is sensitive even when opt-in; must be
trivially revocable and never leak outside the Round, or it violates the privacy moat.

## Tier C — Speculative

### C1. Daily "Pint o'clock" ritual prompt (BeReal-style, opt-in)
**Pitch:** an optional once-an-evening nudge ("what's in your glass?") that invites a quick Spill in
a shared window, manufacturing a nightly ritual.
**User story:** The Lock-In daily habit — BeReal's spontaneity mechanic. [1]
**Effort:** M · **Difficulty:** medium (scheduled client prompt + Spill composer).
**Deps:** notifications (Epic E) for real reach; PWA push is limited without native.
**Why it might fail:** no native app means push is unreliable (out-of-scope constraint); a nag that
can't reach the user is dead weight, and nightly drinking prompts are ethically delicate.

### C2. Then-vs-Now "time-scrub" on the map
**Pitch:** a slider that morphs the map/prices between decades (heritage prices → tonight), using
the shipped then-vs-now data — a playful heritage-meets-live interaction.
**User story:** The Golden Thread (Gen X) + The Ledger heritage — makes sourced history *interactive*. 
**Effort:** L · **Difficulty:** high (temporal data model across the map; senior lane).
**Deps:** then-vs-now price data (shipped) but needs broader historical coverage to feel real.
**Why it might fail:** historical price coverage is thin/uneven — a scrubber over sparse data feels
broken; provenance per-year must stay honest (no invented history).

### C3. One-tap "share with family" postcard (The Family Table)
**Pitch:** a Boomer-friendly, large-text share that turns a Spill into an email/AirDrop-able
"postcard" for family — no feed, no chat, just a beautiful sourced artifact.
**User story:** The Family Table (Boomers) + Ledger accessibility lane — "share with family". 
**Effort:** M · **Difficulty:** medium (reuse the OG-image pipeline + email-to-family from #27-ish
scope).
**Deps:** email delivery path; the OG image generator exists.
**Why it might fail:** email deliverability + no DMs constraint means this is one-directional; if it
feels like a dead-end (no reply loop), engagement may be low — but that's arguably the honest,
calm-tech point for this audience.

### C4. Voice-first Ledger logbook entry
**Pitch:** in Ledger/Legacy mode, a large "hold to speak" button logs a Spill entirely by
voice-to-text — no keyboard, high-contrast confirmation.
**User story:** The Ledger (Boomers/Gen X) large-text voice-friendly logbook (#18 accessibility) —
removes the keyboard barrier without Gen-Z speed loss.
**Effort:** M · **Difficulty:** medium (Web Speech API + the existing large-text Ledger surface).
**Deps:** none (voice-to-text is already a stated Spill-composer default).
**Why it might fail:** Web Speech API support/accuracy varies by browser and struggles in a noisy
pub — must degrade to a big-button manual path, never trap the user in a failed dictation.
