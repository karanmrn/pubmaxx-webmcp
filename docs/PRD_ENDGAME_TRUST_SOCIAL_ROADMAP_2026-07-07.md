# PRD: PUBMAXXING Endgame Roadmap - Trust, CI, Social Core, Drinks, and London Utility

## Problem Statement

PUBMAXXING has become a credible London pub-crawl product: a fast map, pub detail sheets, Pint Drops, feed surfaces, Last Pint transport help, profiles, ratings, messages, rounds, landmarks, borough exploration, and all-drinks groundwork now exist across the repo.

The problem is that the product has grown faster than its production trust model. The demo experience is strong, but the next mergeable work needs to make the whole system reviewable, secure, and coherent:

- GitHub and review automation are not yet clean enough to trust blindly.
- Supabase Preview is failing because remote migration versions are missing locally.
- GitHub Actions currently emits `startup_failure` before job allocation, while Vercel is the reliable green deploy gate.
- Greptile is active and has reviewed recent PRs, but CodeRabbit has not visibly commented on the shipped PR history.
- The current workspace has broad uncommitted work from several agents and should be split into small PRs.
- Several social/privacy flows still rely on self-asserted handles rather than account-backed ownership.
- Public Supabase policies may expose raw social rows if the anon Data API is reachable.
- Comments, reactions, messages, notifications, ratings, and visibility must follow one consistent privacy model.
- The map is much faster after the slim-index work, but venue detail still does heavy server-side full-dataset work on cold start.
- The product vision is broader than pints: all alcoholic and non-alcoholic drinks, stories, ratings, pub crawls, London history, TfL last-train timing, walking/running routes, and shareable social memory.

The end goal is a production-ready Vercel app that feels like Letterboxd + Instagram for pints and pub nights: every pint has a story, every crawl can become a memory, and users can explore London without the app feeling insecure, slow, or demo-only.

## Solution

Execute the next phase as a sequence of small, reviewable PRs. Do not mix infrastructure, auth, social, data ingestion, map performance, and design polish in one broad branch.

The next phase should prioritize:

1. **Trust and release gates first.**
   Make the repository easy for Greptile, CodeRabbit, Vercel, and humans to review. Fix Supabase migration drift, verify CodeRabbit with a small test PR, keep Vercel as the current reliable gate, and document the GitHub Actions startup issue separately from product-code failures.

2. **Account-backed identity before private social claims.**
   Move ownership and privacy-sensitive routes from self-asserted handles to Supabase Auth user identity linked to profiles. Keep anonymous/demo mode only where the product explicitly allows it.

3. **Raw-data privacy before growth.**
   Stop exposing raw community rows through public Supabase reads. Public users should receive sanitized server DTOs or constrained views, not raw social tables.

4. **One coherent social sync model.**
   Comments, reactions, messages, notifications, ratings, saved lists, rounds, and feed items should use the same visibility, ownership, moderation, and cache rules. Parent-hidden content should hide child content everywhere.

5. **Finish the core loop before adding more spectacle.**
   Logging a pint, rating a drink/pub, seeing comments, checking the last train, sharing a crawl, and seeing it on a profile should be fast, obvious, and reliable on mobile and desktop.

6. **Expand from pints to all drinks responsibly.**
   Beer, wine, whisky, gin, vodka, rum, cocktails, shots, low/no-alcohol, soft drinks, coffee, and pub food-adjacent menu items should share one governed drink model with provenance, category filters, and rating semantics.

7. **Make London the product.**
   Landmark stories, pub history, borough pages, TfL timing, walking/running routes, park/view route packs, and "Last Pint" decisions should turn the app from a pub list into a way to fall in love with London.

## Implementation Decisions

### P0: Release Gates and GitHub Hygiene

- Keep Vercel as the reliable automatic deploy gate until GitHub Actions startup failures are resolved.
- Do not treat GitHub Actions `startup_failure` as product-code failure unless jobs actually start and fail.
- Fix Supabase Preview by reconciling remote migration history with `supabase/migrations/`. Do not delete local migrations to make the check pass.
- Verify CodeRabbit with a deliberately tiny PR that changes only a doc line or comment. Acceptance is a visible CodeRabbit check, review, or comment.
- Keep Greptile as a review signal. Target 5/5 by shipping narrow PRs with tests and no unrelated files.
- For each future PR, include:
  - problem statement;
  - files touched;
  - verification commands;
  - Vercel preview URL;
  - Greptile/CodeRabbit status;
  - migration impact;
  - rollback note.
- Split the current broad worktree into independently reviewable branches:
  - CI and migration drift;
  - auth/ownership;
  - comments/reactions/messages sync;
  - all-drinks/rating surface;
  - map performance;
  - mobile/design polish;
  - London storytelling and route packs.
- Do not merge generated screenshots, local agent scratch state, or raw secret files.

### P0: Production Identity and Privacy

- Make `profiles.user_id` plus Supabase Auth the canonical identity for owned operations.
- Replace self-asserted handle trust in messages, notifications, saved pubs/lists, ratings, rounds, comments, crawl stories, profile edits, and destructive Pint Drop actions.
- Keep public browse and explicitly anonymous Pint Drops possible, but do not let anonymous mode own private resources.
- Audit every server route for whether it should use:
  - anonymous public read;
  - signed-in user read;
  - owner-only write;
  - admin-only moderation;
  - service-role internal access.
- Revoke broad public reads on raw social tables or replace them with sanitized `security_invoker` views.
- Ensure public DTOs redact hidden, anonymous, ledger-only, friends-only, and deleted content consistently.
- Move admin auth away from a localStorage shared token toward real auth and httpOnly session handling.
- Move public photo storage toward private buckets with signed URLs or delete/quarantine hidden media on takedown.

### P0: Comments, Reactions, Messages, and Sync Correctness

- Treat parent content visibility as the source of truth for comments and reactions. Hidden or non-public parent content must hide child content.
- Keep messages scoped to conversation participants, not global message IDs or self-asserted handles.
- Make the store/API contract explicit for:
  - list conversations;
  - create conversation;
  - list messages newest-cap/oldest-display;
  - send message;
  - report message;
  - mark read;
  - delete/hide if implemented.
- Add no-store response helpers for all mutable social APIs.
- Keep optimistic UI, but every optimistic state must reconcile with server truth or show a failure state.
- Add browser QA for comments/reactions across feed, venue sheet, profile, and direct drop page.
- Add two-tab or polling/realtime smoke coverage for message/comment sync if feasible.

### P0: Core Logging Loop

- Make "Drop a pint" globally obvious on desktop and mobile.
- Route every entry point to one composer flow rather than multiple divergent posting surfaces.
- Preserve drafts during local navigation and venue switching.
- Allow a user to log:
  - beer/pint price;
  - any drink category;
  - low/no-alcohol drink;
  - photo;
  - story/note;
  - vibe tags;
  - rating if desired;
  - privacy level.
- Make provenance visible for demo, sourced, contributor, and refreshed prices.
- Avoid gamifying alcohol volume or streaks. Celebrate breadth, exploration, responsible timing, and storytelling.

### P1: All Drinks and Ratings

- Keep beer/pints as the original map price layer.
- Add drink category filters for beer, wine, whisky, gin, vodka, rum, cocktails, shots, low/no, soft drinks, coffee, and other.
- Keep a closed category taxonomy shared by TypeScript types, validators, migrations, UI filters, and tests.
- Materialize drink updates from governed price update files into venue menus.
- Distinguish drink ratings from pub ratings:
  - drink rating: the specific pour/menu item;
  - venue context: atmosphere/service/value/story in Visit Reports;
  - crawl rating: route/night experience.
- Use 1-5 stars with 0.5 granularity where ratings are user-facing.
- Hide ranking/aggregate claims below the sample-size floor.
- Keep drink rating summaries sample-size-aware; venue discovery uses Visit Reports,
  not public star leaderboards.

### P1: Live Prices and Data Governance

- Keep refresh scripts allowlist-based. Permissible sources only.
- Scheduled price/drink refreshes should open PRs, never push directly to `main`.
- Every price row must include source label, source URL, licence, observed time, category, and venue matching key.
- Never show stale prices as live.
- Add stale-price UI to map pins, venue sheets, list cards, and OG cards.
- Add CI validation for:
  - full pint dataset;
  - slim venue index;
  - drink update files;
  - TfL line data;
  - POIs;
  - landmark metadata;
  - borough assignment.

### P1: Map Performance and Caching

- Keep the slim-index initial map load. Initial `/map` must not fetch the full pint dataset.
- Prebuild a compact per-venue detail index so `/api/venue/[id]` does not parse and group the full dataset on cold server start.
- Validate `venues_slim.json` directly in `npm run validate-data`.
- Add a performance test that asserts:
  - first pins mark exists;
  - full pint dataset is not requested on initial map load;
  - selected venue detail loads lazily;
  - map canvas stays visible on desktop and mobile.
- Keep `/data/*` cache headers strong.
- Use explicit `Cache-Control: no-store` for mutable social/admin APIs.
- Inspect bundle attribution and keep MapLibre isolated to map routes.
- Fix MapLibre console warnings where style data has null numeric fields.

### P1: Last Pint and TfL Utility

- Support a session destination without storing home addresses by default.

  - half pint only;

  - train risk;
  - live data unavailable.
- Let users share "made the last train" or "one more was safe" moments as optional story badges.
- Add station-adjacent pub suggestions and route-to-station hints.

- Add borough passports showing visited pubs, tried drinks, favourite stories, and saved routes.
- Make "PUBMAXXING" the consistent brand spelling across UI, docs, share cards, and metadata.

### P2: Mobile and Visual Polish

- Run every major release through 390px mobile browser QA.
- Keep the map as the first-class product surface, not a marketing landing page.
- Make controls one-thumb friendly on mobile.
- Avoid crowding the venue sheet with too many chips at once.

- Make empty states operational: every empty feed/list/profile state should have one useful next action.

## Out of Scope

- Native iOS/Android apps.
- Payments, bill splitting, or pub-owner dashboards.
- Taxi booking.
- Storing home addresses by default.
- Scraping competitor price/review sites.
- Encouraging alcohol volume, streaks, or speed drinking.
- Multi-city expansion before London is excellent.
- Replacing MapLibre/OpenFreeMap unless reliability data proves it is required.
- Large unreviewable mega-PRs.
